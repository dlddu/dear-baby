# 단계 스냅샷 저장·재계산 정책 (확정)

## 지위

**확정 문서다** (2026-08-08 제품 결정). 기록의 "작성 당시 단계"를 어떻게
보관할지에 대한 단일 소스다. PRD-002 AC-002-03 과 ENG-011 은 본 문서를 참조한다.

이전까지 이 항목은 "구현 재량" 으로 열려 있었다 (PRD-002 초판 · ENG-011).
본 문서가 그 재량을 닫는다.

## 결정

**물리 저장 + 기준값 정정 시 재계산(백필).**

기록 저장 시점에 단계를 계산해 컬럼에 박아 넣고, 계산의 입력값이 바뀌면
해당 기록들의 컬럼을 다시 계산해 덮어쓴다.

## 근거 — 스냅샷은 순수 함수의 캐시다

단계는 다음 순수 함수의 결과다.

```
stage = f(기록 작성일, 대상 아이의 기준값)
        기준값 = due_date (임신 축) | birth_date (양육 축)
        계산식 = ENG-001
```

작성일은 불변이고 기준값만 변한다. 따라서 **물리 저장은 이 함수의 캐시이고,
백필은 캐시 무효화·재계산**이다. 이 프레이밍이 설계 전체를 규정한다.

- **정합성 조건이 단순해진다**: `f` 의 입력이 바뀌는 모든 지점에서 재계산하면
  캐시는 항상 정확하다. 그 외의 정합성 걱정은 없다.
- **손실이 없다**: 스냅샷은 파생값이라 언제든 원본(작성일 + 기준값)에서 복원
  가능하다. 잘못 덮어써도 다시 계산하면 된다.
- **재계산은 델타 이동이 아니라 전량 재산출이어야 한다.** "예정일이 3일
  밀렸으니 주차에 +3일" 식으로 하면 오차가 누적되고 clamp·경계 처리(ENG-001)를
  건너뛴다. 항상 `f` 를 처음부터 다시 돌린다.

### 소급 계산 대비 이점

| 항목 | 물리 저장 (채택) | 소급 계산 |
|---|---|---|
| 커뮤니티 유사 시기 조회 (ENG-011 ±4주/±1개월) | 컬럼 인덱스로 직접 필터 | 후보 전량 조인·계산 — 인덱스 불가 |
| 일기 카드 칩 렌더 (PRD-008 AC-008-03) | 읽기만 | 목록 항목마다 계산 |
| 기준값 정정 반영 | **재계산 필요 (본 문서의 대상)** | 자동 |
| 기준값 삭제·아이 삭제 후 과거 기록 | 스냅샷이 남아 있어 표시 가능 | 기준값이 없어 계산 불가 |

마지막 행이 부수적 이득이다. 소급 계산은 기준값에 영구 의존하므로, 기준값이
사라지는 경로(아이 정보 삭제 등)에서 과거 기록의 단계를 잃는다. 물리 저장은
그렇지 않다.

## 재계산 트리거

**아래 목록이 정합성의 전부다.** 여기 빠진 경로로 기준값이 바뀌면 캐시가 썩는다.

| # | 이벤트 | 재계산 대상 | 비고 |
|---|---|---|---|
| T1 | `due_date` 수정 | 그 아이의 **임신 축 기록 전량** | 설정 탭 아이 정보 수정 (PRD-006 비기능 요구사항) |
| T2 | `birth_date` 수정 | 그 아이의 **양육 축 기록 전량** | 출생일 오입력 정정. 다태아는 아이별 개별 |
| T3 | 스냅샷 컬럼 최초 도입 (마이그레이션) | 기존 기록 전량 | 1회성. 아래 "도입 시 1회 백필" |

### 재계산 대상이 **아닌** 것

- **출산 전환 (PRD-006 AC-006-06) 은 백필하지 않는다.** 전환은 아이의 축을
  임신 → 양육으로 바꾸지만, **과거 기록을 다시 칠하지 않는다.** 임신 중 남긴
  기록은 출산 후에도 영구히 임신 단계 기록이다 (ENG-011: "작성 후 케이스가
  바뀌어도 기록의 소속은 불변").
  - 전환 시 `birth_date` 가 **처음 설정**되는 것은 T2 의 "수정" 이 아니다.
    전환 이전에는 그 아이의 양육 축 기록이 0건이므로 재계산 대상도 공집합이다.
  - 이 구분을 놓치면 임신기 기록 전체가 "생후 -N개월" 로 오염된다. 구현 시
    가장 틀리기 쉬운 지점이다.
- **시간 경과**는 트리거가 아니다. 날이 지나도 과거 기록의 스냅샷은 그대로다.
  매일 갱신되는 것은 아이의 *현재* 단계(파생값)이지 기록의 스냅샷이 아니다.

### 트리거 누락 방지

트리거를 UI 핸들러마다 흩어 붙이면 새 수정 경로가 생길 때 반드시 빠진다.
**기준값 갱신은 데이터 계층의 단일 지점을 거치게 하고, 재계산을 그 지점에
묶는다.** 기준값 컬럼을 직접 UPDATE 하는 코드 경로를 만들지 않는다.

## 저장 스키마

- 기록 테이블에 단계 컬럼을 둔다: 축 구분 + 값 (예: `stage_kind`,
  `stage_value`). 구체 컬럼명·타입은 구현 시 확정하고 용어집
  (`StageSnapshot`) 에 반영한다.
- **컬럼은 nullable 이어야 한다.** 단계 산출 불가(ENG-001) 상태에서 작성된
  기록은 스냅샷이 없다 (PRD-002 AC-002-05). 재계산 결과가 "단계 없음" 이 되는
  경우도 있다 — 예: 예정일을 5주 이상 과거로 정정하면 ENG-001 판정상 단계
  없음이 되고, 해당 기록들은 NULL 로 덮인다.
- NULL 스냅샷 기록은 커뮤니티 유사 시기 반경 내 그룹에 들지 않는다 (ENG-011).

## 도입 시 1회 백필 (T3)

스냅샷 컬럼을 도입하는 마이그레이션에서 기존 기록 전량을 1회 계산해 채운다.

> **ENG-011 정정**: ENG-011 은 "소급 계산이 항상 가능하므로 기존 기록 백필은
> 불필요하다" 고 기재했으나, 이는 소급 계산 방식을 전제한 서술이었다. 물리
> 저장을 채택한 이상 **도입 시 1회 백필이 필요하다.** ENG-011 해당 문장은
> 2026-08-08 자로 본 문서를 참조하도록 수정됐다. 단, 원래 논지("소급 계산이
> 항상 가능하다")는 유효하며 그것이 백필을 안전하게 만드는 근거다 — 언제
> 돌려도 같은 결과가 나온다.

## 실행 방식

- **동기 실행을 기본으로 한다.** 재계산 대상은 아이 1명의 기록으로 한정되고
  (수십~수백 행), 기준값 수정 트랜잭션 안에서 처리하면 중간 상태가 노출되지
  않는다.
- 다태아 일괄 수정 등으로 대상이 커지면 비동기 배치로 내리되, **완료 전까지
  옛 스냅샷이 보인다**는 점을 UI 가 감내할 수 있는지 확인한다. 오차가 잠깐
  보이는 것이 잘못된 값이 영구히 남는 것보다 낫다.
- 재계산은 **멱등**이다. 같은 입력으로 몇 번 돌려도 결과가 같으므로 실패 시
  단순 재시도로 복구한다.
