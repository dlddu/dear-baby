# Wireframe Reference

dear-baby 앱(`app/`)에서 화면을 만들거나 수정할 때, **`docs/wireframes/`의 인덱스 .md와 SVG를 화면 사양 문서로 먼저 읽도록** 강제하는 스킬.

> **이 스킬의 핵심 원칙**: 와이어프레임이 있는 화면은 와이어프레임이 정답이다. 임의로 레이아웃·문구를 추정하지 않는다.

> **이 스킬의 책임 범위 = SVG → 화면 사양 추출까지**.
> 색·타이포·라운드·간격·그림자·공통 컴포넌트 등 시각 표현의 적용은 별도 스킬 **`design-system`** 이 담당한다. 이 스킬은 그 영역을 다루지 않으며, 시각 표현이 필요한 작업은 design-system 스킬을 함께 따른다.

---

## 0. 적용 범위

**무조건 적용**:
- 새 화면을 추가하거나 기존 화면의 레이아웃·문구·CTA·단계 인디케이터·필드 구성을 수정할 때
- 화면 ID(`Q1`, `A2`, `B0`, `C3` 등)를 다루는 모든 작업
- `docs/wireframes/`에 정의된 영역의 화면을 만지는 모든 작업

**적용 안 함** (다른 스킬/일반 작업):
- 시각 표현 적용(토큰·색·타이포·라운드·간격·그림자·공통 컴포넌트) → **`design-system` 스킬**
- 비즈니스 로직, API 호출, 상태 관리, 데이터 변환 등 화면이 아닌 작업
- `backend/`, `worker/`, `k8s/`, `scripts/` 등 프론트가 아닌 영역

---

## 1. 자료 위치

```
docs/
├── wireframes/                     # 화면 단위 와이어프레임 (이 스킬의 대상)
│   ├── <영역>.md                   # 인덱스 + 화면별 자연어 사양
│   └── <영역>/*.svg                # 화면별 SVG (텍스트·레이아웃 포함)
│   └── (예: onboarding.md, onboarding/{common,case-a,case-b,case-c}.svg)
├── flows/<영역>-flow.md            # 플로우(화면 간 전이) 사양
└── prd/PRD-XXX-*.md                # 기능 요구사항 (필요 시 참고)
```

## 2. 워크플로우

### Step 1. 작업 대상 영역·화면 식별

사용자 요청에서 어떤 영역의 어떤 화면인지 추출한다.
- "온보딩 Q1 만들어줘" → 영역 `onboarding`, 화면 `Q1`
- "Case B의 B2 양육 아이 정보 화면" → 영역 `onboarding`, 화면 `B2`
- "홈 화면 만들어줘" → 영역 `home`(아직 없을 수 있음 → Step 4로 분기)

### Step 2. 인덱스 .md 먼저 읽기

```bash
ls docs/wireframes/                     # 어떤 영역이 정의돼 있는지
cat docs/wireframes/<영역>.md           # 해당 영역 인덱스
```

인덱스 .md에는 화면 목록과 각 화면의 목적·필드·CTA가 자연어로 정리돼 있다. **반드시 SVG보다 먼저 읽는다.**

해당 영역이 없으면 → **Step 4로 분기**.

### Step 3. SVG 와이어프레임 읽기

이 레포의 와이어프레임 SVG는 단순 그림이 아니라, **모든 텍스트·라벨·레이아웃이 SVG 노드로 들어있는 사양 문서**다. `view` 또는 `cat`으로 그대로 읽으면 화면 콘텐츠를 정확히 추출할 수 있다.

```bash
cat docs/wireframes/<영역>/<파일>.svg
```

SVG에서 추출해야 할 것:
- `<title>` — 화면 제목/의도
- `<text>` 노드 — 화면에 실제 표시되는 모든 한국어 문구(질문·라벨·버튼·보조 설명·단계 표시) → **그대로 코드에 사용**
- 화면 하단의 `Q1`, `A2`, `B0`, `C3` 같은 화면 ID 라벨 — 인덱스 .md와 매핑
- 사각형 배치에서 읽을 **구조 정보** (구체 픽셀 값이 아니라 — 아래 표 기준)

문구는 SVG에 적힌 그대로 가져온다. 임의로 다듬지 않는다.

#### SVG에서 따라야 할 것 / 따르지 말아야 할 것 / 의도로 읽을 것

**해석 원칙 — 한 줄로**: 와이어프레임은 "무엇이 어떤 순서로 어떤 그룹에 있나"를 말한다. "그게 어떻게 보이나"는 design-system 스킬의 영역이다.

| 분류 | 와이어프레임에서 읽는 것 | 처리 방식 |
|---|---|---|
| **그대로 따른다 (구조 정보)** | 요소의 종류와 순서: 진행률 바 → "1/3" → 질문 → 보조설명 → 선택지 → 하단 CTA | 코드에 그대로 반영 |
| | 요소들의 그룹화: 카드 안인지 밖인지, 같이 묶이는 영역 | 그대로 반영 |
| | 레이아웃 패턴: 세로 스택 vs 2×2 그리드, 좌측 정렬 vs 가운데 정렬 | 그대로 반영 |
| | 위계: "옵션 버튼이 다음 버튼보다 크고 강조된다" 같은 상대 강약 | 그대로 반영 |
| | 화면 ID(Q1/A2/B0)와 단계 인디케이터의 존재·위치 | 그대로 반영 |
| **따르지 않는다 (와이어프레임 표기일 뿐)** | 절대 픽셀 값: `rx=10`, `width=160`, `height=64`, `font-size=14` — 와이어프레임 캔버스(476×500, 카드 199px) 기준 | 무시. 시각 표현 적용은 **design-system 스킬**에 위임 |
| | 색상: 회색·흰색 톤, `fill="#FFFFFF"`, `stroke="#D3D1C7"` | 무시. **design-system 스킬**에 위임 |
| | 폰트: `font-family="sans-serif"`는 placeholder | 무시. **design-system 스킬**에 위임 |
| | 1px 단색 테두리, 그림자 부재 | 무시. **design-system 스킬**에 위임 |
| **의도로 읽는다 (판단 영역)** | 비율: 옵션 버튼이 카드 폭의 ~80%를 차지 | 상대 비율로 반영 |
| | 간격의 상대적 위계: 질문↔옵션이 옵션↔옵션보다 넓다 | 강약은 유지하여 반영 (구체 값은 design-system 스킬에 위임) |
| | 버튼 높이 차이(64 vs 40): 옵션이 CTA보다 크다 | 절대값이 아니라 "옵션 > CTA" 위계로만 반영 |

### Step 4. 와이어프레임이 **없는** 화면일 때 — 코드 작성 금지, 먼저 합의

해당 영역이 `docs/wireframes/`에 없거나, 영역은 있지만 요청한 화면이 인덱스에 없을 때:

1. 사용자에게 **명시적으로 알린다**: "이 화면은 docs/wireframes/에 정의돼 있지 않습니다."
2. 다음 중 어떻게 진행할지 묻는다:
   - **A)** 먼저 와이어프레임/플로우 문서를 추가한다 (이 경우 화면 코드 작업이 아닌 디자인·문서화 단계로 전환됨 — 사용자와 화면 사양을 합의한 뒤 `docs/wireframes/`에 SVG/MD를 먼저 작성)
   - **B)** 와이어프레임 부재를 PR/커밋 메시지에 명시한 채 임시 구현한다
   - **C)** 작업을 보류한다

사용자 답을 받기 전까지는 **새 화면 코드를 작성하지 않는다**. 기존 화면의 부분 수정은 와이어프레임이 정의한 범위 내에서만 진행한다.

### Step 5. 구현

이 시점에 컨텍스트에 들어 있어야 하는 것:
- 영역 인덱스 .md
- 해당 화면의 SVG (텍스트 노드까지)

이걸 다 봤다는 전제로 코드를 쓴다. 시각 표현 영역의 작업이 함께 필요하면 **`design-system` 스킬을 함께 적용**한다.

이 스킬의 체크리스트(와이어프레임 영역만):

- [ ] 화면에 표시되는 모든 한국어 문구가 SVG와 일치하는가
- [ ] 화면 ID(Q1/A2/B0/C3 등)와 단계 인디케이터가 인덱스 .md의 진행 표시 규칙과 맞는가
- [ ] 요소의 종류·순서·그룹화·정렬이 SVG와 일치하는가
- [ ] 화면 간 전이가 `docs/flows/<영역>-flow.md`와 일치하는가
- [ ] 와이어프레임에 없는 화면을 임의로 추가하지 않았는가

> 시각 표현(토큰·색·타이포·라운드·간격·그림자·공통 컴포넌트) 체크는 **`design-system` 스킬의 체크리스트**를 따른다. 이 스킬에서 별도로 다루지 않는다.

### Step 6. 작업 완료 보고

사용자에게 결과를 보고할 때:
- 어떤 와이어프레임(파일·화면 ID)을 참고했는지
- 와이어프레임과 다르게 처리한 부분이 있으면 그 이유
- 시각 표현 관련 보고는 design-system 스킬의 형식을 따른다

## 3. SVG 와이어프레임 읽는 요령 (실전)

이 레포의 SVG는 한 파일에 여러 화면이 가로로 나열된 구조가 일반적이다 (예: `case-b.svg`는 B0~B6 7개 화면을 한 SVG에 담음).

화면 단위로 분해해서 읽으려면:

1. **`<g transform="translate(X,Y)">` 그룹**을 찾는다 — 각 그룹이 한 화면 카드.
2. 각 그룹 끝/직후의 `<text>` 노드 중 `Q1`, `A2`, `B0` 같은 짧은 라벨이 **화면 ID**다.
3. 그룹 내부의 `<text>` 노드들이 그 화면에 표시되는 실제 문구들이다 — 위에서 아래로 읽으면 자연스러운 화면 컨텐츠 순서가 된다.
4. 진행률 바(`<rect>` 두 개 — 회색 배경 + 어두운 채움)와 `1 / 3`, `2 / 3` 같은 텍스트로 **단계 인디케이터** 사양을 확인한다.

`grep`으로 화면 텍스트만 빠르게 훑고 싶을 때:
```bash
grep -oE '>[^<]+</text>' docs/wireframes/onboarding/case-b.svg | sed 's/[<>/]//g; s/text//g'
```

## 4. 자주 하는 실수 — 미리 차단

이 스킬 책임 범위 안에서의 실수:
- ❌ SVG 텍스트를 "더 자연스럽게" 다듬어서 코드에 넣음 → 문구는 그대로. 변경이 필요하면 사용자에게 묻는다.
- ❌ 와이어프레임에 없는 새 화면을 임의 추가 → Step 4 절차 따르기.
- ❌ 화면 ID를 코드에서 임의로 바꾸거나 무시 → 화면 ID는 인덱스/플로우/PRD/테스트 문서와의 매핑 키이므로 보존.
- ❌ SVG 한 파일을 한 화면으로 오해 → 한 SVG 안에 여러 화면이 가로로 배치돼 있을 수 있음. `<g transform="translate(...)">` 단위로 분해.
- ❌ 인덱스 .md를 안 읽고 SVG부터 봄 → 인덱스가 우선. 인덱스는 화면 의도·필드·CTA를 자연어로 정리해 둔다.

이 스킬 **밖**의 실수 (참고만):
- SVG의 `width=160`, `font-size=14`, 회색 톤, `sans-serif` 같은 표기를 진짜 디자인 값으로 옮기는 실수 → **`design-system` 스킬**의 토큰·색·타이포 규칙을 따른다.

## 5. 빠른 시작 — 한 줄짜리 점검 명령

작업 시작 직전에 한 번 실행해서 사용 가능한 와이어프레임 자산을 한눈에 본다:

```bash
echo "=== Wireframes ==="; ls docs/wireframes/; echo; \
echo "=== Wireframe SVGs ==="; find docs/wireframes -name "*.svg"
```
