# Dear-Baby Frontend Designer

dear-baby 앱(`app/`)에서 **사용자에게 보이는 어떤 것**을 만들거나 수정할 때, 와이어프레임 문서와 디자인 시스템을 먼저 읽고 그 사양을 그대로 따르게 하는 스킬.

> **이 스킬의 핵심 원칙**: 와이어프레임이 있는 화면은 와이어프레임이 정답이다. 임의로 레이아웃을 추정하지 않는다. 와이어프레임이 없는 화면이라면, 코드 작성 전에 사용자와 합의한다.

---

## 0. 적용 범위 — 언제 이 스킬을 따라야 하나

**무조건 적용**:
- `app/src/` 안의 화면(screen), 라우트, 컴포넌트, 스타일을 만들거나 바꿀 때
- 새 화면을 추가하거나 기존 화면의 레이아웃·문구·버튼을 수정할 때
- 색상·타이포·간격·라운드·그림자 값을 코드에 박아 넣을 때

**적용 안 함**:
- 비즈니스 로직, API 호출, 상태 관리, 데이터 변환 등 화면이 아닌 작업
- `backend/`, `worker/`, `k8s/`, `scripts/` 등 프론트가 아닌 영역

## 1. 레포 안 자료 위치 — 한 번에 외워두기

```
docs/
├── wireframes/                     # 화면 단위 와이어프레임
│   ├── <영역>.md                   # 해당 영역의 인덱스 + 화면별 자연어 사양
│   └── <영역>/*.svg                # 화면별 SVG 와이어프레임 (텍스트·레이아웃 포함)
│   └── (예: onboarding.md, onboarding/{common,case-a,case-b,case-c}.svg)
├── design-system/
│   ├── README.md       # 디자인 원칙(따뜻함/부드러움/여백/감성/일관성)
│   ├── tokens.md       # radius, spacing, elevation
│   ├── colors.md       # 컬러 팔레트
│   ├── typography.md   # 폰트, 사이즈, 위계
│   ├── components.md   # 카드/버튼/입력/탭 등 공통 컴포넌트 사양
│   └── patterns.md     # UI/UX 패턴
├── flows/<영역>-flow.md            # 플로우(화면 간 전이) 사양
└── prd/PRD-XXX-*.md                # 기능 요구사항 (필요 시 참고)
```

프론트 코드:
```
app/
├── src/
│   ├── components/   # 재사용 컴포넌트
│   ├── theme/        # 디자인 시스템 매핑 (토큰·컬러·타이포)
│   ├── auth/, voice/, drafts/, ...
│   └── api/, data/, utils/, analytics/
└── package.json      # Expo + expo-router, Gowun Batang / Noto Sans KR / Playfair Display
```

## 2. 워크플로우 — 화면 작업 시 반드시 이 순서로

### Step 1. 작업 대상 영역(영역 = wireframes 하위 그룹) 식별

사용자 요청에서 어떤 영역의 어떤 화면인지 추출한다. 예:
- "온보딩 Q1 만들어줘" → 영역 `onboarding`, 화면 `Q1`(common.svg 안)
- "Case B의 B2 양육 아이 정보 화면 구현" → 영역 `onboarding`, 화면 `B2`(case-b.svg 안)
- "홈 화면 만들어줘" → 영역 `home`(아직 없을 수 있음 → Step 2에서 확인)

### Step 2. 와이어프레임 인덱스 먼저 읽기

```bash
# 현재 어떤 영역의 와이어프레임이 있는지 확인
ls docs/wireframes/

# 해당 영역의 인덱스 .md를 먼저 읽는다
cat docs/wireframes/<영역>.md
```

인덱스 .md에는 화면 목록, 각 화면의 목적·필드·CTA가 자연어로 정리돼 있다. **반드시 이걸 먼저 읽는다.** SVG보다 인덱스가 우선이다.

해당 영역이 없으면 → **Step 5로 분기**.

### Step 3. SVG 와이어프레임 읽기

이 레포의 와이어프레임 SVG는 단순 그림이 아니라, **모든 텍스트·라벨·간격이 SVG 노드로 들어있는 사양 문서**다. `view` 또는 `cat`으로 그대로 읽으면 화면 콘텐츠를 정확히 추출할 수 있다.

```bash
cat docs/wireframes/<영역>/<파일>.svg
```

SVG에서 추출해야 할 것:
- `<title>` — 화면 제목/의도
- `<text>` 노드 — 화면에 실제 표시되는 모든 한국어 문구(질문, 라벨, 버튼 텍스트, 보조 설명, 단계 표시 등) → **이 문구들은 코드에 그대로 사용**
- 화면 하단의 `Q1`, `A2`, `B0`, `C3` 같은 화면 ID 라벨 — 인덱스 .md와 매핑
- 사각형 배치에서 읽을 **구조 정보** (구체 픽셀 값이 아니라 — 아래 표 기준)

문구는 SVG에 적힌 그대로 가져온다. "현재 임신 중이신가요?", "예, 임신 중이에요" 같은 텍스트를 임의로 다듬지 않는다.

#### SVG에서 따라야 할 것 / 따르지 말아야 할 것 / 의도로 읽을 것

**해석 원칙 — 한 줄로**: 와이어프레임은 "무엇이 어떤 순서로 어떤 그룹에 있나"를 말하고, 디자인 시스템은 "그게 어떻게 보이나"를 말한다. **둘이 충돌하면 디자인 시스템이 이긴다.**

| 분류 | 와이어프레임에서 읽는 것 | 처리 방식 |
|---|---|---|
| **그대로 따른다 (구조 정보)** | 요소의 종류와 순서: 진행률 바 → "1/3" → 질문 → 보조설명 → 선택지 → 하단 CTA | 코드에 그대로 반영 |
| | 요소들의 그룹화: 카드 안인지 밖인지, 같이 묶이는 영역 | 그대로 반영 |
| | 레이아웃 패턴: 세로 스택 vs 2×2 그리드, 좌측 정렬 vs 가운데 정렬 | 그대로 반영 |
| | 위계: "옵션 버튼이 다음 버튼보다 크고 강조된다" 같은 상대 강약 | 그대로 반영 |
| | 화면 ID(Q1/A2/B0)와 단계 인디케이터의 존재·위치 | 그대로 반영 |
| **따르지 않는다 (와이어프레임 표기일 뿐)** | 절대 픽셀 값: `rx=10`, `width=160`, `height=64`, `font-size=14` — 와이어프레임 캔버스(476×500, 카드 199px) 기준 | 모두 디자인 토큰으로 환산 |
| | 색상: 회색·흰색 톤, `fill="#FFFFFF"`, `stroke="#D3D1C7"` | `colors.md` 적용 |
| | 폰트: `font-family="sans-serif"`는 placeholder | `typography.md` 적용 (Gowun Batang / Noto Sans KR / Playfair) |
| | 1px 단색 테두리, 그림자 부재 | `tokens.md`의 elevation 적용 |
| **의도로 읽는다 (판단 영역)** | 비율: 옵션 버튼이 카드 폭의 ~80%를 차지 | px가 아닌 %/토큰으로 반영 |
| | 간격의 상대적 위계: 질문↔옵션 간격이 옵션↔옵션 간격보다 넓다 | spacing 토큰으로 환산하되 강약은 유지 |
| | 버튼 높이 차이(64 vs 40): 옵션이 CTA보다 크다 | 절대값이 아니라 "옵션 > CTA" 위계만 가져와 토큰으로 표현 |

### Step 4. 디자인 시스템 매핑

와이어프레임은 **무엇을** 보여주는지를 정의하고, 디자인 시스템은 **어떻게** 보여주는지를 정의한다. SVG의 회색 톤·기본 라운드는 와이어프레임 표기일 뿐, 실제 색상·라운드·그림자는 디자인 시스템을 따른다.

작업 종류별로 읽을 파일:

| 작업 | 먼저 읽을 문서 |
|---|---|
| 새 화면 전체 구현 | `design-system/README.md` → `tokens.md` → `colors.md` → `typography.md` → `patterns.md` |
| 카드/버튼/입력 등 공통 컴포넌트 사용 | `design-system/components.md` (+ `tokens.md`) |
| 색만 조정 | `colors.md` |
| 폰트/사이즈 조정 | `typography.md` |
| 간격·라운드·그림자 | `tokens.md` |
| 화면 간 전이/플로우 | `docs/flows/<영역>-flow.md` |

**금지**: hex 색상, px 라운드/간격, 폰트 패밀리/사이즈를 코드에 직접 박지 않는다. 이미 `app/src/theme/`에 토큰이 매핑돼 있으면 거기 있는 값을 쓰고, 없으면 토큰을 먼저 추가한다.

### Step 5. 와이어프레임이 **없는** 화면일 때 — 코드 작성 금지, 먼저 합의

해당 영역의 와이어프레임이 `docs/wireframes/`에 없거나, 영역은 있지만 요청한 화면이 인덱스에 없을 때:

1. 사용자에게 **명시적으로 알린다**: "이 화면은 docs/wireframes/에 정의돼 있지 않습니다."
2. 다음 중 어떻게 진행할지 물어본다:
   - **A)** 먼저 와이어프레임/플로우 문서를 추가한다 (이 경우 화면 코드 작업이 아닌 디자인·문서화 단계로 전환됨 — 사용자와 화면 사양을 합의한 뒤 `docs/wireframes/`에 SVG/MD를 먼저 작성)
   - **B)** 디자인 시스템과 기존 화면 패턴만으로 임시 구현하되, 와이어프레임 부재를 PR/커밋 메시지에 명시한다
   - **C)** 작업을 보류한다

사용자 답을 받기 전까지는 **새 화면 코드를 작성하지 않는다**. 기존 화면의 부분 수정은 와이어프레임이 정의한 범위 내에서만 진행한다.

### Step 6. 구현

이 시점에 컨텍스트에 들어 있어야 하는 것:
- 영역 인덱스 .md
- 해당 화면의 SVG (텍스트 노드까지)
- 관련 디자인 시스템 문서들
- `app/src/theme/`의 기존 토큰/스타일 매핑

이걸 다 봤다는 전제로 코드를 쓴다. 작성 시 체크리스트:

- [ ] 화면에 표시되는 모든 한국어 문구가 SVG와 일치하는가
- [ ] 화면 ID(Q1/A2/B0/C3 등)와 단계 인디케이터가 인덱스 .md의 진행 표시 규칙과 맞는가
- [ ] 색상·라운드·간격·그림자·폰트가 모두 디자인 토큰을 통해 들어가는가 (직접 hex/px 금지)
- [ ] 카드/버튼/입력은 `design-system/components.md`의 사양과 일치하는가
- [ ] 화면 간 전이가 `docs/flows/<영역>-flow.md`와 일치하는가
- [ ] 따뜻함/부드러움/여백/감성/일관성 — 디자인 원칙 5가지에 어긋나는 부분이 없는가

### Step 7. 작업 완료 보고

사용자에게 결과를 보고할 때 다음을 함께 알린다:
- 어떤 와이어프레임(파일·화면 ID)을 참고했는지
- 어떤 디자인 시스템 문서를 참고했는지
- 와이어프레임/디자인 시스템과 다르게 처리한 부분이 있으면 그 이유

## 3. SVG 와이어프레임 읽는 요령 (실전)

이 레포의 SVG는 한 파일에 여러 화면이 가로로 나열된 구조가 일반적이다 (예: `case-b.svg`는 B0~B6 7개 화면을 한 SVG에 담음).

화면 단위로 분해해서 읽으려면:

1. **`<g transform="translate(X,Y)">` 그룹**을 찾는다 — 각 그룹이 한 화면 카드.
2. 각 그룹 끝/직후의 `<text>` 노드 중 `Q1`, `A2`, `B0` 같은 짧은 라벨이 **화면 ID**다.
3. 그룹 내부의 `<text>` 노드들이 그 화면에 표시되는 실제 문구들이다 — 위에서 아래로 읽으면 자연스러운 화면 컨텐츠 순서가 된다.
4. 진행률 바(`<rect>` 두 개 — 회색 배경 + 어두운 채움)와 `1 / 3`, `2 / 3` 같은 텍스트로 **단계 인디케이터** 사양을 확인한다.

`grep`으로 화면 텍스트만 빠르게 훑고 싶을 때:
```bash
grep -oE '>[^<]+</text>' docs/wireframes/onboarding/case-b.svg | sed 's/[<>/]//g; s/text//g'
```

## 4. 자주 하는 실수 — 미리 차단

- ❌ "와이어프레임 그림 보고 색이 회색이네 → 회색으로 만들자" → SVG의 회색은 **와이어프레임 톤**이지 디자인이 아님. 색은 `colors.md`를 따른다.
- ❌ SVG의 `width=160`, `height=64`, `font-size=14`, `rx=10`을 코드에 그대로 옮기기 → 와이어프레임 캔버스(476×500, 카드 199px) 기준 placeholder. 모두 spacing/radius/typography 토큰으로 환산.
- ❌ SVG에 그림자가 없으니 그림자도 빼기 → 와이어프레임은 깊이를 표현하지 않음. 그림자는 `tokens.md`의 elevation을 따른다.
- ❌ "옵션 버튼 64, 다음 버튼 40"을 절대값으로 박기 → 절대값이 아니라 "옵션이 CTA보다 큼"이라는 **위계**만 가져와서 토큰으로 표현.
- ❌ SVG의 텍스트를 "더 자연스럽게" 다듬어서 코드에 넣음 → 문구는 그대로 가져온다. 변경이 필요하면 사용자에게 묻는다.
- ❌ 디자인 시스템을 안 읽고 hex/px 직접 박기 → 항상 토큰 경유.
- ❌ 와이어프레임에 없는 새 화면을 임의 추가 → Step 5 절차 따르기.
- ❌ 화면 ID를 코드에서 임의로 바꾸거나 무시 → 화면 ID는 인덱스/플로우/PRD/테스트 문서와의 매핑 키이므로 보존.

## 5. 빠른 시작 — 한 줄짜리 점검 명령

작업 시작 직전에 한 번 실행해서 사용 가능한 와이어프레임/디자인 자산을 한눈에 본다:

```bash
echo "=== Wireframes ==="; ls docs/wireframes/; echo; \
echo "=== Wireframe SVGs ==="; find docs/wireframes -name "*.svg"; echo; \
echo "=== Design System ==="; ls docs/design-system/; echo; \
echo "=== Theme code ==="; ls app/src/theme/ 2>/dev/null
```
